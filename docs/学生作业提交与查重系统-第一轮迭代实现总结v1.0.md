## 1. 引言

### 1.1 目的

第一轮迭代的目标是交付一个**可运行的核心闭环版本**：用户管理 → 课程管理 → 作业发布 → 学生提交 → 文本/代码查重 → 教师评审 → 成绩发布。本文档回答三个问题：

1. 第一轮**实际实现了哪些功能**，实现到什么深度？
2. 哪些第一轮需求条目**部分实现或尚未实现**？差异具体是什么？
3. 系统当前**能否正常运行**，已知哪些技术缺陷与风险？

### 1.2 核对方法

| 步骤 | 内容 | 结论来源 |
| --- | --- | --- |
| 静态走查 | 后端 9 个业务包全部 Controller / Service / Mapper / 迁移脚本；前端 11 个视图 + 12 个 API 模块 + 路由与状态；引擎 12 个 Python 文件 | 源码 |
| 运行态实测 | 登录（教师/学生）、课程与作业列表、提交列表、评审保存与提交、可见性开关、查重报告读取 | HTTP 请求实测 |

## 2. 完成度总览

### 2.1 量化结论

以 SRS-R1 的 38 条 [R1] 功能需求条目为分母：

| 判定 | 条数 | 占比 | 说明 |
| --- | --- | --- | --- |
| ✅ 完整实现 | 14 | 37% | 功能闭环，前后端均可用 |
| ⚠️ 部分实现 / 简化实现 | 20 | 53% | 核心路径可用，但缺少需求要求的某一环 |
| ❌ 未实现 | 4 | 11% | 第一轮条目内，代码中无任何实现 |

**核心结论：第一轮交付的"可运行闭环"在**身份、课程、作业、提交、查重执行与报告查询、站内通知**这六个域是成立且可用的；但在"评审与成绩"域存在系统性缺口——后端接口基本齐备，前端入口大量缺失，导致**成绩发布、评审工作台、逐维度打分、提交进度看板**四条功能"接口已写、界面未接"，教师实际无法在界面上完成成绩发布。这是第一轮最需要正视的交付缺口。**

### 3.4 提交管理（FR-S）

| 需求 | 功能 | 实现入口 | 实现要点 |
| --- | --- | --- | --- |
| FR-S-01 作业提交 | ✅ | `POST /api/v1/assignments/{assignmentId}/submissions`（仅 STUDENT）、`POST /assignments/{id}/files` | 成员须为 `ACTIVE` 的 `STUDENT`（403 `SUBMISSION_FORBIDDEN`）；作业须 `PUBLISHED`、课程须 `ACTIVE`、未开放→409 `SUBMISSION_NOT_OPEN`；在线文本上限 100 万字符；附件去重、≤10 个；**首版本强制 `integrityConsent`**（422 `INTEGRITY_CONSENT_REQUIRED`），后续版本继承首次签署时间；**幂等键**：`Idempotency-Key` 请求头或 body 字段双通道（≤128 字符），命中则回放原提交；前端支持在线文本 + 多文件上传（进度条、类型白名单过滤、100MB/10 个前端限制、前端生成 UUID 幂等键） |
| FR-S-02 多版本与生效版本 | ✅ | 同上 + `POST /api/v1/submissions/{id}/effective` | `pg_advisory_xact_lock` 事务级锁串行化同一学生的版本递增；`versionNo = max + 1`；不允许多版本且已有历史→409 `MULTI_VERSION_NOT_ALLOWED`；`LAST_SUBMISSION` 规则自动把旧生效版本置 `false` 并让新版本生效；`MANUAL` 规则下新版本不自动生效，由教师 `setEffective` 指定（先清同学生既有生效标记，审计 `submission.effective`）；数据库层 `uk_submission_effective` 部分唯一索引保证每人仅一份生效版本 |
| FR-S-03 状态查询 | ✅ | `GET .../submissions/mine`、`GET .../submissions?allVersions=`、`GET /submissions/{id}` | 学生本人视角与教师视角（教师默认只看生效版本，"全部版本"开关切换）；状态字典覆盖 `SUBMITTED / CHECKING / CHECK_FAILED / CHECK_COMPLETED / REVIEWED / PUBLISHED` 并关联查重任务；前端以 el-tag 着色展示，并显示"是否生效"标记 |
| FR-S-05 迟交处理 | ✅ | 提交时判定 + `ReviewService.lateDeduction` | `allowLate && lateDeadlineAt >= now` 才受理并置 `isLate=true`、记录 `effectiveDeadlineAt`；窗口外 409 `SUBMISSION_DEADLINE_PASSED`。**扣分公式已实现**：`daysLate = ceil((submitted_at - effective_deadline_at) / 86400s)`（至少 1 天），读 `system_config.submission.late_penalty`（种子值 `{"type":"DAILY_PERCENT","value":5,"maxDeduction":20}`）→ 按天扣原始分 5%，累计上限 20 分，`max(0)` 后 `min(maxDeduction)`，保留两位小数；`finalScore = max(0, rawScore - deduction)` |
| FR-S-06 文件校验 | ⚠️ | `POST /api/v1/assignments/{assignmentId}/files` | 空文件 422、大小上限来自 `system_config.file.max_size_bytes`（默认 100MB）、扩展名白名单 = **全局 `file.allowed_extensions` ∩ 作业级 `allowedFileTypes`**、`safeName()` 清洗路径分隔符与 `\r\n\t`（防目录穿越/头注入）、SHA-256 摘要、附件所有权与 `object_key` 前缀校验、附件不可被重复挂载、下载时 `no-store` 且仅本人或课程管理者可访问。**缺口：无真实病毒扫描** —— 上传插库时 `scan_status` 恒为 `'CLEAN'`，`download()` 的 `INFECTED/FAILED` 拦截分支无处产生该状态；也无文件魔数 / MIME 一致性校验（只认扩展名） |

**超出需求的额外能力**：输入指纹（`onlineTextDigest` + 规范化 `inputDigest` = 文本与各文件 sha256 的摘要，用于查重去重与快照复现）。

### 3.5 查重引擎（FR-K）

#### 3.5.1 已实现

| 需求 | 功能 | 实现要点 |
| --- | --- | --- |
| FR-K-05 任务队列（部分） | ✅ 核心机制成立 | DB 队列：`FOR UPDATE SKIP LOCKED LIMIT 1` 按 `scheduled_at, created_at` 原子抢占，置 `lease_owner / lease_until / heartbeat_at` 与 `attempt+1`（`repository.py::claim`）；任务阶段推进 `QUEUED → PREPROCESSING → COMPARING → REPORTING → SUCCEEDED`；失败重试采用指数退避 `min(300, 15*2^(attempt-1))` 秒回退 `QUEUED`；达上限置 `FAILED` + `submission.status='CHECK_FAILED'`；Java 侧 `GET /api/v1/check-tasks/{id}` 映射阶段文案与进度百分比（5/20/65/90/100），并按 `attempt >= max_attempts` 分为 `PERMANENT / RETRYABLE` 两类错误 |
| FR-K-01 文本查重（部分） | ✅ 算法链路成立 | 文本抽取支持 `.pdf`（pypdf 逐页）、`.docx`（python-docx 段落 + 表格单元格）、纯文本；编码链 `utf-8-sig → utf-8 → gb18030 → latin-1`；NFKC 归一化 + 5 类引用标注剔除 + 空白折叠；3-gram N-gram 特征；Jaccard + 余弦（token 频率）+ SimHash（64 位，blake2b，按词频加权）+ 汉明相似度；句子级与全文级两层，综合分 `0.45*Jaccard + 0.35*Cosine + 0.20*Hamming` |
| FR-K-02 代码查重（部分） | ✅ 归一化链路成立 | 注释剥离（字符状态机，保留字符串与换行，覆盖 `//`、`/* */`、Python `#`）；标识符按出现顺序重命名为 `ID1..IDn`、字符串→`<STR>`、数字→`<NUM>`；`== != <= >= && \|\| -> => ::` 作独立 token；Token 4-gram Jaccard + `difflib.SequenceMatcher.ratio()` + 词频余弦；支持 10 种语言（`.java .py .c .h .cpp .cc .hpp .js .ts .go .cs .rs`）；支持单文件或多个独立源码文件 |
| FR-K-04 查重报告（部分） | ✅ 报告生成与查询闭环 | 报告 JSON 写入对象存储（`reports/{assignment}/{submission}/{task}/report.json`），DB 存摘要：`overall_score / text_score / structure_score / level / source_count / report_digest / links`；报告信封含 `schemaVersion`、`algorithmVersion="check-1.0.0"`、`generatedAt`、`thresholds`、`params(ngramSize/simhashBits/libraries/maxSources)`、`excludedItems`；报告版本 `report_version = max+1` 且 `is_current` 单值（先批量置 false 再插新行）；DB 触发器 `guard_report_immutable` 保证 `check_report` 除 `is_current` 外任何字段不可更新（**报告不可篡改落到 DB 触发器层**）；查询接口含 `current` / 历史版本 / `segments` / `sources` / `manifest` / `html` / `verify` 摘要签名校验；HTML 报告带严格 CSP（`default-src 'none'; sandbox`）与 `no-store`，内容全部 HTML 转义 |

#### 3.5.2 与需求的差距

| 差距 | 具体表现 |
| --- | --- |
| 无 MinHash / 倒排索引 / LSH 初筛 | 设计文档与 SRS 要求"倒排索引 + 局部敏感哈希初筛后精排"，实际是**候选句 × 全部来源 × 全部来源句的 O(N×M) 全量两两比较**；`requirements.txt` 仅 4 个依赖，未引入 datasketch/NumPy |
| 无段落级粒度 | SRS 要求"句子级、段落级、全文级"三层，实际只有句子级 + 全文级两层 |
| 文本总分取 `max()` | `text_score = max(sentence_score, full.max * 0.85)`，少量大段复制即可拉高总分，存在过判倾向 |
| 中文未分词 | `TOKEN_PATTERN` 把每个汉字当作一个 token，长中文句区分度差 |
| 无 AST、无编辑距离 | 代码归一化是正则 + 手写状态机；`difflib` 是 LCS 近似而非 Myers/Levenshtein；**函数级兜底（`compare_code`）在主链路是死代码，报告路径不调用它** |
| 高亮粒度粗 | `highlightRanges` 是整句全区间 `[0, len(text)]`，不是真实重叠片段定位；**代码模式恒为空数组** |
| 无双栏对比视图 | 需求要求"左右双栏对比"，实际是"分段列表 + 来源摘录列表"的非对齐并列，来源只显示约 240 字符摘录 |
| `excludedItems` 为静态文案 | 报告里的排除项是硬编码常量，不反映任何真实剔除统计 |
| 比对库写了但不读 | `library_entry` 只被写入（自动入库本班库），**读取来源完全绕开库表**，直接查 `submission`；历届库完全未实现（`source_type` 恒为 `"CLASS"`）；白名单库配置能被读取但从不影响计算；`library_watermarks` 字段存在但从未写入 |

## 5. 超出第一轮需求的额外能力

以下能力在需求条目中未列出，但代码中确实实现，属于第一轮的额外交付：

1. **令牌刷新与会话失效体系**：`tokenVersion` 机制使登出/改密/改角色/停用均可让旧令牌立即失效；前端 401 自动刷新并单飞重放。
2. **ETag / If-Match 乐观并发控制**：课程编辑与归档、作业编辑、查重配置、量规更新共用 `Etags`（`row-{version}`），冲突返回 412。
3. **定时发布调度器**：`AssignmentPublishScheduler` 60 秒周期 + 条件 UPDATE CAS，课程归档自动取消定时。
4. **提交幂等键双通道**：请求头或 body，命中回放原记录。
5. **报告不可篡改的双保险**：DB 触发器 `guard_report_immutable` + `report_digest` 摘要签名校验接口。
6. **报告只读 HTML 渲染**：服务端拼装，带严格 CSP `sandbox` 与 `no-store`。
7. **报告版本历史**：`report_version` 倒序 + `is_current` 单值保证。
8. **输入指纹**：`onlineTextDigest` / `inputDigest` 支撑快照复现。
9. **TraceId 全链路透传**：`TraceIdFilter` + CORS 暴露 + 审计 `trace_id` + 异常响应 `traceId`。
10. **评审结果可见性开关**：作业级 `results_visible`，与成绩发布形成双通路。
11. **文件类型白名单求交**：全局 `file.allowed_extensions` ∩ 作业级 `allowed_file_types`。
12. **查重失败状态兜底**：入队异常时置 `CHECK_FAILED` 并写 `check.enqueue.failed` 审计。
13. **演示数据引导**：`DemoDataInitializer` 一键生成四类演示账号、课程、作业与通知。
14. **助教角色**：`ASSISTANT` 拥有 `review:write` 权限点（但见 §6.2 第 3 条的接口拦截问题）。
15. **手动重查重**（原标 [R2] 的 FR-K-07，已提前实现并含幂等键）。

## 6. 已知缺陷与风险

### 6.1 高风险（影响正确性 / 可用性）

| # | 问题 | 根因 | 影响 |
| --- | --- | --- | --- |
| R1 | **查重任务永久挂死** | `claim()` 只匹配 `status='QUEUED'`，**全库无任何"过期租约 → 回 QUEUED"的回收代码**（`ix_check_task_lease` 索引建了但无查询使用）。worker 在 `COMPARING` 阶段崩溃/OOM 后任务永久滞留中间态 | 学生侧永远显示"正在比对"，且无出口；违反 FR-K-05"重启后未完成任务可恢复执行" |
| R2 | **成绩发布无用户入口** | 后端 `POST /assignments/{id}/grades/publish` 完整，但前端零调用 | FR-R-07（P0）在界面上不可用，第一轮核心闭环的最后一环断裂 |
| R3 | **维度分与批注无法录入** | `AssignmentDetailView.vue` 硬编码 `dimensionScores: []`、`annotations: []` | FR-R-03 / FR-R-02 在界面上不可用，量规定义了维度也无法逐维度打分 |
| R4 | **文本查重无候选检索** | `load_sources` 一次性把最多 300 份来源全文读入内存，`report.py` 做 O(候选句 × 来源句) 全量比较 | 大班（几百人）+ 启用历届库时线性恶化；NFR-P-04（10 万字 ≤60 秒 P95）无基准测试支撑 |

### 6.2 中风险（功能正确性偏差）

| # | 问题 | 根因 | 影响 |
| --- | --- | --- | --- |
| R5 | **重试次数与需求不符** | `fail()` 用 `attempt < max_attempts` 判断，而 `claim()` 已把 `attempt+1`，`max_attempts=3` 实际只有 2 次重试（共 3 次尝试） | FR-K-05"自动重试最多 3 次"名不副实 |
| R6 | **查重失败未告警管理员** | `fail()` 只向**提交学生**插入 `CHECK_FAILED` 通知，无管理员/教师收件人 | 违反 FR-K-05"仍失败标记查重失败并告警管理员" |
| R7 | **分数计算取 max 倾向过判** | `text_score = max(sentence_score, full.max * 0.85)` | 引用公式/定义段等正当重合可能把总分拉到 SEVERE |
| R8 | **比对库"写而不读"** | `load_sources` 直接查 `submission`，`library_entry` 只被写入；白名单配置能被读取但从不参与计算 | FR-K-08 实质未生效；`library_entry.fingerprint_key` 写入但从不参与读取 |
| R9 | **助教被评审接口拦截** | `ReviewController` 的 `hasAnyRole('TEACHER','ADMIN')` 放行助教，但 `ReviewService.requireSubmissionManageAccess → CourseService.requireManage` 只承认 `ADMIN / owner / INSTRUCTOR` | 助教"名义可评审、实际 403" |
| R10 | **压缩包文件清单接口恒空** | `GET /check-reports/{id}/manifest` 读 `app.file_classification`，但全库无该表写入方 | 接口返回 `totalFiles: 0` |
| R11 | **代码查重函数级证据不产生** | 报告路径直接调 `structure_similarity(整文件)`，含"函数级兜底 ×0.95"的 `compare_code` 无任何调用方 | 设计文档承诺的函数级匹配与 FR-K-02"文件级/函数级匹配"在真实流程中不成立，`highlightRanges` 恒空 |
| R12 | **成绩发布不发通知、不可修改** | `ReviewService.publish` 不调用 `NotificationService`；`save()` 对 `PUBLISHED` 抛 `REVIEW_PUBLISHED` | FR-R-07"发布后修改须留痕并重新通知"整条缺失；FR-N-01 缺一类通知 |
| R13 | **登录限速不可横向扩展** | `LoginAttemptGuard` 用进程内 `ConcurrentHashMap` | 多实例部署下限速不共享 |
| R14 | **对象存储孤儿报告** | `save_report` 先写 S3 后开 DB 事务，回滚无补偿 | 事务失败留下孤儿对象 |

## 7. 结论

1. **第一轮迭代的核心闭环在数据与业务规则层面是成立的**：从登录鉴权、课程花名册、作业发布（含定时发布）、学生多版本提交（含幂等与诚信声明）、文本/代码查重执行、报告生成与不可篡改保护，到教师评审草稿与提交、站内通知，主链路可以端到端跑通，且安全与并发控制（Argon2、乐观锁、事务级行锁、幂等键、DB 触发器）落地质量较高。
2. **"评审与成绩"域是本轮最明显的交付缺口**，且性质是**前后端不配套**而非功能未开发：后端接口（评审队列、成绩查询、单份/批量发布、可见性开关）基本齐备，但前端**零调用**，导致成绩发布、评审工作台、逐维度打分、提交进度看板四条功能在界面上不可用。
3. **查重引擎的工程质量与算法深度需要第二轮重点加固**：任务队列缺少租约回收与重启恢复，文本查重缺少候选检索索引，代码查重缺少 AST 归一化，比对库存在"写而不读"的结构性问题。
4. **测试与 CI 是下一轮最先要补的工程能力**：当前后端与前端零测试，CI 没有质量门禁，冒烟脚本不覆盖查重链路，任何对查重状态机或事务顺序的改动都缺乏回归保障。

第二轮迭代的范围与排期见《学生作业提交与查重系统-第二轮迭代开发计划说明 V1.0》。
