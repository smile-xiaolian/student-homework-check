## 1. 引言

### 1.1 目的

明确第二轮迭代的目标、范围、优先级、技术债修复、数据与接口变更、里程碑排期、风险与验收标准，作为开发、测试与验收的共同基线。

### 1.2 第一轮的结论摘要（本计划的出发点）

| 维度 | 第一轮状态 | 对第二轮的直接影响 |
| --- | --- | --- |
| 功能完成度 | 38 条 [R1] 条目：14 完整（37%）、20 部分（53%）、4 未实现（11%） | 需先补齐核心闭环的断点 |
| 最大缺口 | 后端接口齐备、前端入口缺失（成绩发布、评审队列、统计看板、比对库配置） | **P0 以"前后端打通"为主** |

| 查重算法 | 无候选检索索引、无 AST、无段落级、比对库写而不读 | P1/P2 分批加固 |

### 1.3 迭代策略

第二轮不再追求"再扩一个功能域"，而是按**三条主线**推进，并在每条主线上有明确的收尾判据：

- **主线 A：闭环打通**（P0）——把第一轮后端已写好的能力接到界面上，使教师能完成"评审 → 发布成绩 → 学生查看"，学生能完成"自查 → 查看报告 → 查看评语"。
- **主线 B：可靠性与工程能力**（P0）——修复查重任务挂死与告警缺失，建立后端/前端测试与 CI 门禁，使后续改动有回归保障。
- **主线 C：能力补全**（P1/P2）——比对库管理、查重算法升级、压缩包/预查重、申诉延期、小组与互评等 [R2] 需求，按业务价值与依赖关系分期。

## 4. P0 条目详述（必须完成）

### 4.1 FR-R2-01 成绩发布前端入口

**背景**：后端 `POST /api/v1/assignments/{id}/grades/publish`（空 body = 整作业发布，带 `submissionIds` = 逐条发布）与 `GET /assignments/{id}/grades`、`GET /submissions/{id}/grade` 均已实现并可用，但前端 `reviewApi.publishGrades / grades / grade` 三个方法**零调用**，界面无任何"发布成绩"按钮。这是第一轮最严重的断点。

**实现要点**
- 在评审工作台（见 FR-R2-03）新增"成绩"Tab：分页展示 `submissionId / submitterName / versionNo / rawScore / lateDeduction / finalScore / checkVerdict / comment / published / publishedAt`。
- 支持按 `reviewStatus` 筛选"已评审未发布"；行级"发布"按钮 + 表头多选"批量发布"。
- 批量发布调用 `publishGrades(assignmentId, submissionIds)`；单份发布传单个 id 数组。
- 发布前弹二次确认，展示"将发布 N 份成绩，发布后学生立即可见且不可撤回"。
- 发布成功后刷新列表与提交状态标签（`PUBLISHED`）。

**验收要点**：教师在界面上完成发布 → 学生收到站内通知 → 学生详情页可见成绩与评语；审计出现 `grade.publish` 事件且 `publishedCount` 正确。

### 4.2 FR-R2-02 成绩发布通知与"修改留痕 + 重新通知"

**背景**：`ReviewService.publish` 不调用 `NotificationService`（Java 侧目前仅发出 `ASSIGNMENT_PUBLISHED` 一种通知）；`save()` 对 `PUBLISHED` 直接抛 `REVIEW_PUBLISHED`，FR-R-07"发布后成绩仍可修改，修改须留痕并重新通知"整条缺失。

**实现要点**
- `publish()` 成功后按 `submission.submitterId` 逐条写入 `GRADE_PUBLISHED` 通知，标题含作业名与最终分，`targetType='SUBMISSION'`。
- 新增 `PATCH /api/v1/submissions/{id}/grade`（成绩更正）：仅课程管理者；入参 `rawScore / checkVerdict / comment / reason`；`reason` 必填（≥8 字符）作为更正理由。
- 更正时写 `app.grade_modification` 表（见 §6），记录修改前后值、修改人、理由、时间，形成修改链；审计事件 `grade.modify`。
- 更正后重新推送 `GRADE_PUBLISHED` 通知，内容标注"成绩已更新"。
- 学生端成绩详情增加"更正记录"折叠区（仅显示时间与理由，不显示历史分值）。

**验收要点**：发布→学生收到通知；更正→学生收到更新通知；审计中可检索到 `grade.modify` 且含理由；修改链行数 = 更正次数。

### 4.3 FR-R2-03 独立评审工作台页面

**背景**：后端 `GET /api/v1/assignments/{id}/review-queue` 已返回 `checkScore / checkLevel / reviewStatus / gradeStatus / late / submittedAt`，前端 `reviewApi.queue` 与 `ReviewQueueItem` 类型**零调用**；教师只能在作业详情页的提交列表里逐行评审。

**实现要点**
- 新增路由 `/assignments/:id/review`（角色 TEACHER/ADMIN），`ReviewWorkbenchView.vue`。
- 筛选：评审状态（未评/草稿/已评审/已发布）、查重等级（PASS/WARNING/SEVERE）、是否迟交、学生姓名/学号模糊搜索；排序：相似度、学号、提交时间、状态；分页（默认 20）。
- **`SEVERE` 提交置顶**（FR-K-09 要求的"严重级在评审工作台置顶预警"——当前排序仅 `is_late DESC, submitted_at ASC`，需改为 `check_level='SEVERE' DESC, is_late DESC, submitted_at ASC`）。
- 顶部指标条复用评审队列统计：待评审 / 已评审 / 已发布 / 查重失败 / 迟交。
- 行操作：查看提交、查看查重报告、评审、发布成绩、下载文件。
- 支持从课程页与作业页两个入口进入。

**验收要点**：筛选与排序生效且参数透传到接口；分页正确；`SEVERE` 行排在最前；教师可在一页内完成从筛选到评审的连续操作。

### 4.4 FR-R2-04 量规逐维度打分录入与草稿回显

**背景**：后端 `dimension_scores` 完整入库（`ReviewService.save` 原样写 `app.grade.dimension_scores`），但前端 `AssignmentDetailView.vue` 保存评审时硬编码 `dimensionScores: []`。

**实现要点**
- 评审抽屉读取 `assignment.rubricDefinition`，按维度渲染打分控件（0 ~ `maxScore`，步进 0.5）。
- 若量规定义了 `levels`，用等级选择器与分值联动。
- 维度分实时汇总为 `rawScore`（可手动微调，微调时提示"总分与维度分不一致"）。
- 保存草稿后回显全部字段（维度分、结论、评语、批注）；用 `expectedRowVersion` 处理并发（后端已支持 `REVIEW_VERSION_CONFLICT`）。
- 未定义量规时给出兜底：仅提供原始得分，并在界面上提示"该作业未配置评分量规"。

**验收要点**：三维度量规逐维度打分 → 提交 → 学生端"教师评审"栏目展示各维度分与合计；刷新页面后草稿回显正确；两人并发修改同一提交触发 412。

### 4.5 FR-R2-05 提交进度看板页面

**背景**：`AnalyticsService.submissionProgress` 已返回 `memberCount / submittedCount / lateCount / checkingCount / completedCount / unsubmittedCount / submitRate`，前端零调用。

**实现要点**
- 作业详情页新增"提交进度"Tab（仅课程管理者可见）：环形图展示提交率，卡片展示已交/未交/迟交/查重中/已完成，表格展示未提交学生名单（学号/姓名）。
- 支持"催交"按钮（写入 `REMIND` 通知给未提交学生），标记为可选增强。

**验收要点**：数字与后端接口一致；未提交名单可查；催交后学生收到通知。

### 4.6 FR-R2-06 比对库选择与排除项配置 UI

**背景**：`AssignmentEditDialog.vue` 硬编码 `libraries: ['CLASS']` 与 `exclude: {references:true, template:true}`，界面上只有一个禁用且恒选中的复选框；独立的 `GET/PUT /assignments/{id}/check-config` 在前端零调用。

**实现要点**
- 比对库多选：本班库（禁用且恒选，符合 BR-16）、历届库（依赖 FR-R2-14，先以配置项占位）、白名单库（依赖 FR-R2-14）。
- 排除项开关：引用标注、参考文献、模板代码、公共代码；每项有说明文案。
- 保存走 `updateCheckConfig`（带 `If-Match`），校验通过后刷新展示。
- 与 FR-R2-14 解耦：即使历届库/白名单库尚未落地，UI 也须正确展示与保存本班库 + 排除项。

**验收要点**：关闭"引用标注"排除后，同一提交重查的报告中 `excludedItems` 不再包含引用项，相似度上升；配置以 `config_snapshot` 固化到任务。

### 4.7 FR-R2-07 查重任务租约回收与重启恢复

**背景（最高风险）**：`claim()` 只匹配 `status='QUEUED'`，全库**无任何"过期租约 → 回 QUEUED"的回收代码**；`ix_check_task_lease` 索引已建但无查询使用。worker 在中间态崩溃后任务永久滞留，学生侧永远显示"正在比对"且无出口。违反 FR-K-05"服务重启后未完成任务可恢复执行"。

**实现要点**
- 新增租约回收器（**Java 侧 `@Scheduled`，5 秒周期**），执行：
  ```sql
  UPDATE app.check_task SET status = 'QUEUED', lease_owner = NULL, lease_until = NULL,
         error_code = 'LEASE_EXPIRED', error_detail = '任务租约过期，自动重新入队',
         scheduled_at = now(), updated_at = now()
  WHERE status IN ('PREPROCESSING','COMPARING','REPORTING')
    AND lease_until IS NOT NULL AND lease_until < now()
  ```
  用 `RETURNING id` 判定是否发生回收，回收数写入监控指标与审计。
- 同一任务被回收的次数记录在 `check_task`（新增 `requeue_count` 列），超过阈值（默认 3）转 `FAILED` 并告警，避免坏任务无限循环。
- 与心跳配合：`heartbeat()` 只在 `lease_owner` 匹配时续租（现状已如此），避免"回收器与存活 worker 抢同一任务"。
- worker 启动时**不主动接管**旧任务，统一由回收器按租约到期时间恢复，保证语义简单可测。

**验收要点（必须有集成测试）**：任务置 `COMPARING` + `lease_until = now() - 1s` → 回收器运行后任务回到 `QUEUED` 且被 worker 重新领取；`requeue_count` 达阈值后任务终态 `FAILED` 且通知管理员。

### 4.8 FR-R2-08 查重重试次数语义与失败告警管理员

**背景**：`fail()` 用 `attempt < max_attempts` 判断，而 `claim()` 已把 `attempt + 1`，`max_attempts = 3` 实际只有 2 次重试（共 3 次尝试）；且失败只向**提交学生**插入 `CHECK_FAILED` 通知，未告警管理员。

**实现要点**
- 统一语义为"**最多 `max_attempts` 次尝试**"：判定改为 `attempt <= max_attempts`（或改为在 `claim()` 前不自增，二选一，须写单测锁定语义）。
- `fail()` 达上限时同时向 `ADMIN` 角色全部用户 + 课程负责人写入 `CHECK_FAILED_ADMIN` 通知，内容含任务 id、提交人、失败原因摘要、重试次数。
- 失败原因分类（`PERMANENT / RETRYABLE` 已在 Java 侧映射）写入通知，便于运维判断。
- 提供 `POST /api/v1/check-tasks/{id}/retry`（管理员/课程管理者）手工重入队，用于运维兜底。

**验收要点**：`max_attempts=3` 时共执行 3 次尝试；第 3 次失败后学生与管理员都收到通知；管理员可手工重入队。

### 4.9 FR-R2-09 测试能力与 CI 质量门禁

**背景**：后端 `backend/src/test` 目录不存在（Dockerfile 与 CI 均 `-DskipTests`）；前端无 `*.spec.*`；引擎 13 个单测全为纯算法；CI 无 lint / SCA / 镜像构建；冒烟脚本不覆盖查重链路。

**实现要点**
- **后端单元测试**：优先覆盖纯逻辑 —— 迟交扣分公式（含边界：恰好 1 天、超过上限、`rawScore=0`）、量规校验、查重配置校验、`Etags` 解析、`LoginAttemptGuard` 状态机。
- **后端集成测试**：引入 Testcontainers（PostgreSQL 16 + MinIO），覆盖：迁移可执行、提交幂等回放、生效版本唯一约束、评审状态机、成绩可见性双通路、租约回收。
- **前端测试**：引入 Vitest + Vue Test Utils，优先覆盖：状态字典映射、提交表单校验、评审抽屉表单（含维度分汇总）、API 模块的 URL 与错误码映射。
- **引擎测试**：补齐 `repository.py` 事务测试（claim 并发互斥、fail 重试语义、save_report 事务顺序与孤儿对象）、`content.py` 多格式抽取测试。
- **查重金样本集**：建立固定金样本目录（文本 6 组 + 代码 6 组，含"抄袭/改写/正当引用/无相似"四类标注），作为 `engine/tests` 的回归输入，CI 每次执行并输出误报/漏报矩阵。
- **CI 门禁**：`backend` job 去掉 `-DskipTests` 并加 JaCoCo 覆盖率阈值（行覆盖 ≥ 40% 起步）；新增 `lint` job（后端 `spotless`/`checkstyle`、前端 `eslint` + `prettier`）；新增 `scanning` job（`trivy` 镜像扫描 + `safety` 依赖扫描）；新增 `image-build` job 验证三个 Dockerfile 可构建；`smoke-test.ps1` 扩展为覆盖查重全链路（提交 → 入队 → 领取 → 报告 → 评审 → 发布）。

**验收要点**：`main` 分支合入必须通过上述门禁；PR 显示覆盖率与扫描结果；金样本集结果有基线数字并可对比。

### 5.1 FR-R2-10 在线文档预览与文本批注

**背景**：`app.grade.annotations jsonb` 与前端类型 `annotations: Array<{id; text; quote?}>` 已预留（含 `quote` 锚点），但前端恒传空数组，后端无 `quote/anchor` 结构校验，无文档定位接口。

### 5.2 FR-R2-11 反馈附件上传与展示

**背景**：`app.grade.feedback_file_id` 字段在 schema 中存在，但全仓无写入方；`ReviewSaveRequest` 无附件字段，视图也不返回附件。

**实现要点**

**验收要点**：教师上传评语附件 → 发布 → 学生在成绩详情下载成功；非本人提交者访问返回 403。

### 5.3 FR-R2-12 批量打分与批量下载 ZIP

**背景**：全后端 grep `zip|bulk|batch` **零命中**；批量打分无端点；批量下载只有单文件流式下载（`ByteArrayResource` 全量载入内存）。

**实现要点**
- `POST /api/v1/assignments/{id}/grades/batch-score`：入参 `submissionIds`（≤200）+ 规则（`ALL_MAX` / `BY_CHECK_LEVEL` / `FIXED`）+ 原因；执行前返回 `preview`（受影响条数与分值变化预览），确认后执行；审计 `grade.batch_score`。
- `GET /api/v1/assignments/{id}/submissions/zip?ids=`：流式打包 ZIP（**须改为流式写入，禁止全量载入内存**），包含提交在线文本（`.txt`）与附件；每个文件路径按 `{学号}_{姓名}_v{版本}/` 组织；单次上限 50 份，超过返回 422 并要求分批。
- 二次确认预览端点 `POST .../preview`（dry-run），符合 FR-R-06"须二次确认并预览影响范围"。
- ZIP 内存与 IO 边界测试（单份 100MB 附件不 OOM）。

**验收要点**：勾选 5 份提交批量赋满 → 预览显示 5 份 → 确认后全部生效并审计；下载 ZIP 成功且文件可打开、无内存尖峰。

**实现要点**

### 5.5 FR-R2-14 比对库管理（历届库 / 白名单库）

**背景**：`app.check_library`（`library_type IN ('CLASS','HISTORICAL','INTERNET','LITERATURE','WHITELIST')`）与 `app.library_entry` 表结构完整，但 **Java 侧零 Controller/Service 引用**；唯一写入方是引擎自动建本班库。且引擎 `load_sources` 直接查 `submission`，**写库不读库**。

**实现要点**
- 新增 `LibraryController`：库 CRUD、`POST /libraries/{id}/entries`（入库，支持按课程/学期/学号批量导入）、`DELETE /libraries/{id}/entries/{entryId}`（剔除）、启停。

**验收要点**：启用历届库后，对历史作业的提交重查，报告来源列表出现历史条目且 `libraryStatus.HISTORICAL='OK'`；白名单库中的参考材料不参与相似度计算。

### 5.7 FR-R2-17 作业关闭与归档

**背景**：`publish()` 会拒绝 `ARCHIVED` 作业再发布，但**全后端无代码把作业置为 `ARCHIVED`，也无关闭/归档端点**，属死分支。

**实现要点**

### 5.9 FR-R2-19 病毒扫描与 MIME 一致性

**实现要点**
- 上传后 `scan_status='PENDING'`，异步扫描任务（Java `@Scheduled` 或独立 worker）调用 ClamAV 守护进程（compose 增 `clamav` 服务）；结果写 `scan_status`（`CLEAN / INFECTED / FAILED`）。
- 提交时仅允许 `CLEAN`（现有校验已支持）；`INFECTED` 通知学生并提供替换入口。
- MIME 一致性：读取文件头 magic number 与扩展名比对，不一致 422 `FILE_MIME_MISMATCH`。
- 扫描超时（默认 60s）按 `CLEAN` 放行并记录日志（降级策略），避免阻塞提交主流程。

## 12. 风险与应对

| 编号 | 风险 | 等级 | 应对 |
| --- | --- | --- | --- |
| RK-01 | 查重算法升级引入回归，误报/漏报恶化 | 高 | 金样本集先建后改；每次改动输出对比矩阵；`algorithmVersion` 递增保证可复现与可回滚 |

| RK-03 | 引入 tree-sitter / datasketch / ClamAV 后镜像体积与 CI 时间膨胀 | 中 | 先做选型评审（记录体积、安装时间、无 grammar 降级策略）；ClamAV 用独立 compose 服务而非打进 engine 镜像 |
| RK-04 | POI/EasyExcel 依赖引入后后端镜像与启动变慢 | 中 | 选型对比后选轻方案；导入走流式逐行，禁止全量载入 |

| RK-06 | P1/P2 范围过大导致排期失控 | 中 | 严格 P0 优先；M2 结束时做一次范围裁剪评审，P2 未启动项转入第三轮并登记 |
