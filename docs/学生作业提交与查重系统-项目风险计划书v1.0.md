## 1. 引言

### 1.1 编制目的

本计划书旨在为学生作业提交与查重系统建立一套贯穿项目全生命周期的风险管理机制，具体目的如下：

- **统一认知**：为 2 人团队确立一致的风险识别口径、评估标准与处置原则，避免因主观判断差异导致风险遗漏或处置失当；
- **前置应对**：在 CP2 设计基线评审节点识别开发阶段主要风险，提前配置技术预研、时间缓冲与 AI 赋能资源，将"被动救火"转为"主动管控"；
- **支撑决策**：为检查点评审、变更控制与功能裁剪提供量化依据，当风险触发时能够快速启动预案、调整交付边界；
- **沉淀经验**：形成可追溯的风险登记表与应对记录，为项目复盘与后续迭代提供知识资产。

### 1.2 适用范围

本计划书适用于学生作业提交与查重系统自需求基线确认（CP1）至项目验收答辩（CP5）的全过程，覆盖需求、设计、开发、测试、部署、验收各阶段的技术、管理、质量、外部环境与人员五类风险。

## 2. 项目风险概述

### 2.1 项目背景与目标

学生作业提交与查重系统面向高校作业教学场景，建立"发布—提交—查重—评审—反馈—申诉—归档"的完整教学闭环，16 周内由 2 人团队借助 AI 工具完成交付。需求基线 v1.2 共 68 条功能需求（P0 级 43 条），其中 V1.2 新增压缩包代码查重扩展（WBS 5.5.11~5.5.16 共 6 个子任务）。

项目的核心业务目标为：全生命周期可追溯、查重结果可信可复现、高峰期稳定可用、多角色边界清晰、压缩包查重安全可控。

### 2.2 风险管理目标

| 维度 | 目标 |
| --- | --- |
| 识别 | 在 CP2 前完成 20 项初始风险识别，覆盖率 ≥ 95% 已知风险类别 |
| 评估 | 所有高风险与中风险项具备明确评分、责任人、应对策略与应急预案 |
| 处置 | 高风险项 100% 落实缓解措施并设专人监控；中风险项 100% 具备应对策略 |
| 监控 | 每周跟踪高风险，每两周跟踪中风险，检查点复审全部风险 |
| 闭环 | CP4 前关键路径相关风险降至可接受水平；CP5 完成风险应对效果评估 |

### 2.3 风险管理原则

1. **预防为主**：技术预研前置（W4~W5）、设计基线先行，降低不确定性向开发阶段传导；
2. **量化决策**：以"概率 × 影响"评分驱动分级与资源分配，避免凭直觉处置；
3. **分级处置**：高风险必有应急预案与专人监控，中风险定期跟踪，低风险观察升级；
4. **AI 赋能与人工兜底并重**：以 AI 工具提升产能与覆盖面，同时保留人工审查与裁剪兜底，防范过度依赖；
5. **动态更新**：风险登记表随检查点滚动复审，状态、概率与影响随进展实时更新。

## 4. 风险管理方法

### 4.1 风险管理流程

```
风险识别 → 风险评估（概率×影响） → 风险分级 → 应对策略制定 → 风险监控 → 状态更新
    ↑                                                              │
    └──────────────────── 定期复审 / 触发复审 ──────────────────────┘
```

风险识别来源于需求评审、WBS 拆解、技术预研、历史经验与 AI 辅助分析；评估采用"概率等级 × 影响等级"量化评分；分级后按阈值匹配处置原则与报告频率；监控阶段跟踪触发条件，状态变化时回写登记表，形成闭环。

### 4.2 风险评估标准

**概率等级**：

| 等级 | 标签 | 概率区间 | 说明 |
|:----:|:----:|:--------:|------|
| 1 | 极低 | < 10% | 几乎不会发生 |
| 2 | 低 | 10% ~ 30% | 不太可能但有可能 |
| 3 | 中 | 30% ~ 60% | 有合理可能性 |
| 4 | 高 | 60% ~ 85% | 很可能发生 |
| 5 | 极高 | > 85% | 几乎必然发生 |

**影响等级**：

| 等级 | 标签 | 影响描述 | 判定标准 |
|:----:|:----:|---------|---------|
| 1 | 可忽略 | 对项目几乎无影响 | 进度延误 < 1 天，成本增加 < 1% |
| 2 | 轻微 | 影响有限，可内部吸收 | 进度延误 1~3 天，局部功能降级 |
| 3 | 中等 | 需调整计划或资源 | 进度延误 3~7 天，部分检查点偏移 |
| 4 | 严重 | 影响关键交付或质量 | 进度延误 1~2 周，检查点无法通过 |
| 5 | 灾难 | 项目目标无法达成 | 核心功能不可用，项目失败 |

> **风险评分 = 概率等级 × 影响等级**（取值范围 1~25）。

### 4.3 风险分级阈值

| 风险评分 | 风险等级 | 处置原则 | 报告频率 |
|:--------:|:--------:|---------|---------|
| 15 ~ 25 | 🔴 **高风险** | 必须有明确应对策略 + 应急预案 + 专人监控 | 每周复审 |
| 8 ~ 14 | 🟡 **中风险** | 需有应对策略 + 定期监控 | 每两周复审 |
| 1 ~ 7 | 🟢 **低风险** | 记录观察，触发时升级 | 检查点复审 |

### 4.4 风险应对策略类型

| 策略 | 说明 | 适用场景 |
|:----:|------|---------|
| 规避 | 消除风险源或绕开风险路径 | 需求裁剪、技术方案替换 |
| 缓解 | 降低概率或影响程度 | 技术预研、增加测试、AI 辅助 |
| 转移 | 将风险责任转给第三方 | 外包、保险、第三方服务 |
| 接受 | 知悉并承担风险后果 | 低风险、成本过高的缓解 |
| 储备 | 预留时间/资源缓冲应对 | 进度缓冲、应急人力 |

### 6.1 技术风险（TR）

#### TR1 — 查重算法精度不达标

| 项目 | 内容 |
|------|------|
| **风险描述** | 文本/代码查重核心算法的准确率、召回率不达预期，误判（误报率高）或漏判（漏报率高）导致学术争议或查重结果不可信 |
| **风险类别** | 技术风险 |
| **概率** | 中（3） |
| **影响** | 严重（4） |
| **风险评分** | 12 🟡 |
| **触发条件** | 黄金样本集回归测试准确率 < 90%；代码查重对变量重命名/注释添加等混淆手段漏判；文本查重对同义改写敏感度不足 |
| **影响范围** | 查重引擎核心（WBS 5.5.2/5.5.3/5.5.4）、查重报告可信度、申诉量增加、用户信任度 |
| **关联 WBS** | 5.5.2 文本查重引擎、5.5.3 代码查重引擎、5.5.4 混合查重、6.5 查重专项测试 |
| **关联检查点** | CP3（W9 第一轮迭代）、CP4（W14 专项测试） |

**应对策略（缓解）**：

| 措施 | 时间窗口 | 责任人 |
|------|---------|:------:|
| W4~W5 技术预研阶段完成算法原型验证，用黄金样本集评估候选算法 | W4~W5 | 黄小容 |
| 多算法证据融合：文本采用 n-gram + Winnowing + 语义相似度；代码采用 AST + Token 序列 + AST 节点指纹 | W7~W9 | 黄小容 |
| 阈值可配置化，不同作业类型/语言支持独立阈值调优 | W7~W9 | 黄小容 |
| AI 辅助算法原型生成与参数调优，加速迭代 | W7~W9 | 黄小容 |
| 建立黄金样本回归测试集，每次算法变更自动回归 | W9 起 | 黄小容+林伟豪 |
| 查重报告透明化：展示匹配片段、来源、相似度明细，支持人工复核 | W9~W10 | 黄小容+林伟豪 |

**应急预案**：若 CP3 时算法精度仍不达标，将查重结果定位为"辅助参考"而非"判定依据"，增加教师人工复核环节；降低自动判定阈值，减少误判争议。

### 8.3 风险触发与升级机制

```
风险触发条件满足
  → 风险状态变更为"已发生"
  → 24h 内通知项目经理（黄小容）
  → 评估实际影响
  → 启动应急预案
  → 若影响超预期 → 升级至干系人/CCB
  → 记录应对过程与结果
  → 更新风险登记表
```

### 8.4 风险状态定义

| 状态 | 说明 |
|:----:|------|
| 观察中 | 已识别但未触发，定期复审 |
| 监控中 | 活跃监控，触发条件部分满足 |
| 已发生 | 触发条件已满足，正在执行应对 |
| 已闭环 | 风险已消除或已降至可接受水平 |
| 已接受 | 评估后决定接受，不再主动应对 |

### 9.2 风险报告内容模板

每份周风险简报至少包含：本期新增/关闭风险编号、高风险项状态变化、已启动应急预案清单、下周重点关注项与所需决策。检查点评审输出对应版本的风险登记表更新稿。

### 9.3 信息透明与可追溯

所有风险状态变更、应对动作与应急启动均记录于风险登记表的"处置记录"栏与项目配置库，保证决策可追溯、应对可复盘，避免口头沟通导致的信息流失。

## 10. 应急预案

### 10.1 功能裁剪方案（触发条件：MR1 产能严重不足 / MR4 进度延误超 1 周）

| 优先级 | 功能模块 | WBS | 处置 |
|:------:|---------|:---:|------|
| P0 必交付 | 用户权限/课程/作业/提交 | 5.1~5.4 | 必须交付 |
| P0 必交付 | 文本查重/代码查重/报告/调度 | 5.5.2/5.5.3/5.5.5/5.5.6 | 必须交付 |
| P0 必交付 | 评审与反馈 | 5.6 | 必须交付 |
| P1 应交付 | 压缩包查重（V1.2） | 5.5.11~5.5.16 | 降级为一期（解压+分类+基础比对） |
| P1 应交付 | 通知/统计/系统管理 | 5.8/5.9/5.10 | 简化实现 |
| P2 可延后 | 申诉与延期 | 5.7 | 延至 V1.1 |
| P2 可延后 | 预查重/手动重查/分级预警 | 5.5.7/5.5.8/5.5.10 | 延至 V1.1 |
| P2 可延后 | 混合查重/比对库管理 | 5.5.4/5.5.9 | 延至 V1.1 |

### 10.2 查重降级方案（触发条件：TR1 算法精度不达标）

- 查重结果定位为"辅助参考"而非"判定依据"
- 增加教师人工复核环节
- 降低自动判定阈值，减少误判争议
- 报告中标注"算法版本与置信度"，提示人工复核

### 10.3 压缩包查重降级方案（触发条件：TR2 复杂度超预期）

- 一期：解压安全校验 + 文件分类 + 文件级 + 目录级两层比对
- 二期（V1.1）：代码归一化高级策略 + 项目结构级比对

### 10.4 性能降级方案（触发条件：TR4 性能不达标）

- 并发目标从 500 降至 300（满足课程级使用）
- 部署文档标注性能边界
- 优化热点接口，增加缓存层

### 10.5 人员不可用方案（触发条件：PR1 成员长期不可用）

- 仅保留另一成员能独立完成的功能范围
- 与干系人协商调整交付目标
- 启动最大功能裁剪方案
